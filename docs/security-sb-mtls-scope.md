# mTLS между микросервисами — scope для СБ (май 2026)

## Текущая модель Converter (как есть)

- **Периметр:** TLS терминируется на **Nginx на хосте** (публичный HTTPS, обычно только 443 наружу). До приложений снаружи доходит уже после прокси.
- **База данных (опционально):** для Postgres сервисов `keycloak_db`, `nsi_db`, `documents_db` в репозитории предусмотрено **включение server-side TLS** и постепенное усиление клиентов (`sslmode`, Keycloak `KC_DB_TLS_*`). Подробности: `docs/security-db-encryption.md`.
- **East-west (межконтейнерный HTTP):** сервисы общаются по **обычному HTTP** внутри изолированных Docker-сетей (`converter_backend`, `converter_db` с `internal: true` для БД). Это стандартная схема «TLS на edge + доверенная внутренняя сеть».

Такая модель **не** является полноценным **mTLS между всеми парами микросервисов** в смысле взаимной проверки клиентских сертификатов на каждом HTTP-вызове.

## Что означает требование «mTLS между всеми микросервисами»

Под полным mTLS обычно понимают:

- у **каждого** сервиса свой клиентский сертификат;
- **каждый** входящий запрос проверяет сертификат клиента;
- централизованное или mesh-управление выдачей, ротацией и отзывом сертификатов.

Для стека на Docker без сервис-меша это означает либо **ручную** прокладку TLS/mutual TLS между парами сервисов (практически не масштабируется), либо внедрение **service mesh** (например Istio/Linkerd на Kubernetes, или эквивалент с sidecar/proxy на каждом поде/контейнере).

## Позиция на один проход работ (май 2026)

**Полная mesh-mTLS между всеми микросервисами в этом репозитории не внедряется** в рамках текущего этапа: это отдельный инфраструктурный проект (mesh, PKI, наблюдаемость, SLO, миграция с Docker Compose).

## Что потребуется для будущего sign-off СБ по east-west mTLS

1. **Выбор платформы:** Kubernetes + service mesh **или** явно согласованный альтернативный контур (например mTLS через sidecar на каждом сервисе с единым CA).
2. **PKI:** корпоративный или выделенный CA, политика жизненного цикла сертификатов, отзыв, аудит.
3. **Политика по умолчанию:** deny-all + явные разрешения между сервисами (как минимум на уровне mesh AuthorizationPolicy / аналогов).
4. **Исключения:** совместимость с Keycloak, Celery/RabbitMQ, MinIO — у каждого протокола свои нюансы TLS/mTLS; возможны отдельные каналы (TLS на AMQP, отдельный listener и т.д.).
5. **Эксплуатация:** мониторинг сертификатов, алерты на истечение, процедуры аварийного отключения.

После согласования архитектуры с ИБ/ЦОД можно зафиксировать целевую схему в отдельном ADR и плане миграции.
